# Spec (Requirements) — CacheCollapse

*Course: SE-401 Information Security · CEP. This is a security research testbed, not a product for sale.*

## 1. Goal

Build a small system of connected programs (all inside Docker) that shows how a
"cache stampede" can overload a database and knock a website offline — even
though the attacker only sends normal-looking web requests. Then show that two
defenses (rate limiting and cache locking) keep the site working, and that both a
simple rule and a small ML model can detect the attack live. The whole thing is
shown through live dashboards and a presentable control-panel frontend.

## 2. Users

- **The student team (5 members)** — run the experiments and read the results.
- **The attacker (a script)** — a load generator that sends a sudden burst of
  requests for the same product right after its cache entry expires.
- **Normal users (a script)** — a load generator that sends steady, light traffic.
- **The course instructor / audience** — watches the live demo and reads the final
  report with the graphs and numbers.
- **The presenter (a team member)** — drives the live demo from the frontend
  control panel: starts traffic, launches the attack, toggles defenses, and shows
  the dashboards reacting in real time.

The product traffic ("normal users" and "attacker") is generated by scripts.
The only human-facing screen is the **live dashboard + control panel** used to run
and present the demo — there is still no end-user login or accounts.

## 3. Features

The system is made of 9 small parts, each in its own Docker container:

1. **Nginx (front door)** — receives all requests and passes them to the web app.
   Can be switched to also limit how many requests one source may send per second
   (rate limiting, via `limit_req`).
2. **Flask web app** — answers one request: `GET /products/<id>`. It first checks
   the cache; on a miss it reads the database, then saves the answer in the cache.
   Can be switched to use a lock (cache locking) so many misses for the same
   product cause only **one** database read.
3. **Redis cache** — stores product answers for a short time (TTL, e.g. 10 seconds).
   Also holds the SETNX mutex key used by cache locking.
4. **PostgreSQL database** — holds the real product data. This is the victim that
   gets overloaded during the attack.
5. **Load generator** — sends (a) normal steady traffic (Locust) and (b) a precise,
   timed burst of many requests for the same product id (Python burst script).
   Starting numbers: TTL ~10s, burst ~500 requests/second.
6. **Monitor / detector** — watches the system and raises an alert. It runs **two
   detectors side by side so the report can compare them**:
   - **Rule-based:** *IF database load is high AND response time is high AND cache
     misses suddenly spike → raise an alert.* (No AI, explainable.)
   - **ML-based:** an unsupervised anomaly detector (scikit-learn `IsolationForest`)
     trained only on normal-baseline metrics; it flags the attack as an anomaly.
     No manual labeling needed. Features = the metrics already collected.
   The monitor also writes all metrics to a **CSV file** each second (this doubles
   as the detectors' input and the raw data for report graphs).
7. **Prometheus** — time-series collector; scrapes metrics from the web app and a
   Postgres exporter so metrics are stored over time for live dashboards.
8. **Grafana** — ready-made dashboards that read Prometheus and draw live charts
   (latency, DB load, cache miss rate, CPU/memory) — the "industry tool" view.
9. **Frontend dashboard + control panel** — a presentable, custom web UI built
   for the live demo and presentation. It is the showpiece and must:
   - **Live monitoring:** real-time charts (updating each second via
     Server-Sent Events / WebSocket) of response time, DB queries/sec,
     cache hit vs miss, CPU/memory — so the audience *watches* the stampede happen.
   - **Live attack/defense controls:** buttons to start normal traffic, launch the
     burst attack, and toggle each defense (rate limiting, cache locking) on/off
     live — so the effect is visible on the charts instantly.
   - **Live detector status:** shows the rule-based alert and the ML anomaly score
     in real time, lights up when the attack is detected, and displays the measured
     detect time and recover time.
   This frontend talks to a small live API exposed by the **monitor** container
   (SSE/WebSocket for metrics, simple control endpoints for the buttons).
   Suggested stack (beginner-friendly): static HTML + Chart.js + SSE, or a small
   React app. Final tech chosen in the design phase.

The system must support running **three experiments** and saving their numbers:

- **Experiment 1 — Normal baseline:** steady traffic only. Expect stable, low DB load.
- **Experiment 2 — Attack, no protection:** burst attack with defenses OFF.
  Expect DB overload, slow/failed responses (the DoS).
- **Experiment 3 — Attack + protection:** same attack with rate limiting AND
  cache locking ON. Expect the site stays available and the detector fires.

**Measurements saved for each run:** response time (average and worst),
CPU and memory use per container, number of database queries, cache hit/miss
rate, number of failed requests, time to detect the attack, time to recover.

## 4. Not included (not building now)

- No end-user web app, login, or user accounts. The only human screen is the
  demo's live dashboard + control panel (not a product the public would use).
- No real customer data, real payments, or real passwords (fake seed data only).
- No live deployment to the internet — everything runs locally on Docker Compose.
- No Kubernetes / Docker Swarm (we only mirror those patterns; Compose is enough).
- No defense beyond the two chosen (rate limiting, cache locking). Others — e.g.
  probabilistic early expiration, stale-while-revalidate — are future work, not now.

## 5. Success checks (simple yes/no)

1. `docker compose up` starts all 9 containers and they can talk to each other.
2. `GET /products/1` returns correct product data (from DB on first call,
   from cache on the next call within the TTL).
3. **Baseline:** with normal traffic, database query count and response time stay low.
4. **Attack works:** with defenses OFF, the burst makes DB load spike, response
   time jump, and some requests fail — i.e. the stampede is clearly visible.
5. **Cache locking works:** with locking ON, a burst of N misses for the same
   product produces ~1 database read instead of N.
6. **Rate limiting works:** with rate limiting ON, excess burst requests are
   rejected/slowed before they reach the database.
7. **Protection holds:** with both defenses ON, the site stays available during
   the attack (few/no failed requests, response time stays reasonable).
8. **Rule detection works:** the rule-based detector raises an alert during the
   attack and its time-to-detect is recorded.
9. **ML detection works:** the IsolationForest detector flags the attack as an
   anomaly, and its time-to-detect / false-alarm rate can be compared to the rules.
10. **Live dashboard works:** the custom frontend shows live charts updating each
    second, the control buttons change the system live, and the detector status
    lights up on attack — all demo-able in front of an audience.
11. **Grafana works:** Prometheus+Grafana show the same metrics as polished,
    ready-made dashboards.
12. All numbers from the three experiments are saved (CSV) and can be turned into
    graphs for the report.

## Decisions (locked in with the user)

1. **Detection:** both **rule-based AND ML** (IsolationForest), compared in the report.
2. **Load tool:** **Locust** for normal traffic + a **Python burst script** for the
   precise timed attack.
3. **Attack scale (starting numbers):** TTL **~10s**, burst **~500 requests/second**
   for one product id. May be tuned during experiments.
4. **Metrics / dashboards:** CSV logger (report data) **+ Prometheus + Grafana**
   (industry dashboards) **+ a custom live frontend dashboard & control panel**
   (the demo showpiece). Focus is on **live monitoring and live data**.
5. **Frontend:** yes — a presentable custom web UI is in scope (live charts +
   attack/defense controls + detector status). Exact stack picked in design phase.
